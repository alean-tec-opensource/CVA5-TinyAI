# Governance & Decision-Making

This project operates under a vendor-neutral, transparent, and meritocratic governance model led by the **Technical Steering Committee (TSC)**.

## Technical Steering Committee (TSC)
The Technical Steering Committee (TSC) is responsible for defining, enforcing, and arbitrating the project's decision-making process, technical roadmap, and architectural choices.

## Decision-Making Process
* **Lazy Consensus (Default):** Routine fixes, minor technical improvements, and documentation updates proceed via Lazy Consensus. Proposals are approved if no TSC member objects within **72 hours**.
* **Simple Majority (50% + 1):** Unresolved technical disagreements, architectural debates, or feature disputes are elevated to a formal TSC vote requiring a simple majority.
* **Supermajority (2/3):** Charter updates, licensing changes, security disclosures, and electing new TSC members require a 2/3 supermajority vote of the entire TSC.

## Vendor Neutrality Limit
To preserve vendor neutrality, no single corporate entity or organization may hold more than **33%** of total voting seats on the TSC.

## Kanban Process: Plan-of-Record and Decision logs 

1. To document TSC decisions, we will use the [issues functionality on the platform](about:blank) following a [kanban approach](https://en.wikipedia.org/wiki/Kanban_%28development%29).
2. New issues do not need a [Label](about:blank); but one of three labels will be used to manage issues on our [kanban board](aout:blank):  
- **[READY]** for new issues that have gone through an initial review and approved to go on kanban.
- **[IN-PROGRESS]** for issues that are progressing without as expected.
- **[STUCK]** issues that have a bug, need help, are waiting for an answer, or are prevented from  continuing.
3. Closed issues do not need a Label, but we recommend using one of the four available for closed issues:
- **[DONE]** project has been reviewed and considered completed
- **[duplicate]** issue is a duplicate of (Issue ID)
- **[invalid]** after review the issue was deemed to not represent an actual issue
- **[will-not-fix]** upon review it has been decided not to work on this issue
4. Issues that require multiple steps may spun a new "project" within this group; these issues shall include the following elements in their description:
- **[Role of Assignee]** Define the role the person assigned to work on the issue should assume: Developer, Lead, Reviewer, etc
- **[Scope]** Define the items on which the work is expected to be done.
- **[Action]** Define what is the action to be performed within that scope: Develop a software program, Review a new feature proposal, approve a new process change, etc.
- **[Timeline]** include a target date or estimated time commitment to the task to help assist its progress.
- For example:
-- As a [Role of Assignee], take the [Scope] and [Action] by the [Timeline].

# How to Contribute Code

## Developer Certificate of Origin (DCO)
All commits must include a DCO sign-off line (`git commit -s`) certifying that you have the right to submit the code under the project's open-source license.

## Issue Protocols
When contributing to this repository, consider to first discuss the change you wish to make by creating an issue on this repository before making a change; it will probably save all involved time and effort. 
* Before starting work on major features or breaking changes, open an issue to discuss your proposal with the community and TSC.
* Bug fixes can proceed directly to a Merge Request (MR).

### Merge Request (MR) Checklist
1. All automated GitLab CI/CD pipeline checks must pass.
2. Code must include unit tests covering new functionality or bug fixes.
3. At least one approval from an active Committer or TSC member is required prior to merging.

## AI-Generated Code Guidelines & Policy

Artificial Intelligence tools (such as GitHub Copilot, Gemini, ChatGPT, and Claude) are powerful tools for accelerating development. However, AI-generated code shall follow the following **Core Prociples**.

1. **Human Accountability:** The human committer is 100% responsible for all code merged into the repository. Blaming AI for bugs, security flaws, or broken pipelines is invalid.
2. **Review First, Merge Second:** Treat AI-generated code with the same scrutiny as code written by an untrusted third party or junior intern.
3. **No Unfiltered Pasting:** Code generated by LLMs must be understood, tested, and vetted before being committed. Developers must not submit AI-generated code they cannot explain line-by-line during code review.
4. **Hallucinated Package Protection:** AI models frequently hallucinate non-existent libraries or dependencies (a vector used for "slopsquatting" or dependency confusion attacks). Manually verify that every imported package is genuine and actively maintained.
5. **Automated SAST & Secret Scanning:** Force all AI-assisted contributions through automated Static Application Security Testing (SAST) and secret detection pipelines before human review.
6. **AI slop:** Maintainers should look out for overly verbose, repetitive, or unnecessarily complex boilerplate code that AI models tend to generate.
7. **Style-guide preservation:** Require AI-assisted code to conform strictly to the project’s existing style guide and architecture patterns.
8. **AI Assistance Disclosure:** identify AI-assisted code
> **AI Assistance Disclosure:**
> Generative AI (e.g., Gemini/Copilot) was used to draft initial test cases in `tests/test_parser.sv`. 
> All logic was manually reviewed, refactored, and tested by the committer.

# Contribution Covenant
In the interest of fostering an open and welcoming environment, we as contributors and maintainers pledge to making participation in our project and our community a harassment-free experience for everyone, regardless of age, body size, disability, ethnicity, gender identity and expression, level of experience, nationality, personal appearance, race, religion, or sexual identity and orientation.

## Our Collaborative space 
Examples of behavior that contributes to creating a positive environment include:
* Using welcoming and inclusive language
* Being respectful of differing viewpoints and experiences
* Gracefully accepting constructive criticism
* Focusing on what is best for the community
* Showing empathy towards other community members

Examples of unacceptable behavior by participants include:
* The use of sexualized language or imagery and unwelcome sexual attention or advances
* Trolling, insulting/derogatory comments, and personal or political attacks 
* Public or private harassment
* Publishing others' private information, such as a physical or electronic   address, without explicit permission
* Other conduct which could reasonably be considered inappropriate in a   professional setting

## Scope
This pledge applies both within project spaces and in public spaces when an individual is representing the project or its community. Examples of representing a project or community include using an official project e-mail address, posting via an official social media account, or acting as an appointed representative at an online or offline event. Representation of a project may be further defined and clarified by project maintainers.
